# Plan 076: live stream with System audio — a stalled output kills the mic for good, and your own stream loops back as an echo

Status: investigated 2026-09-28; **IMPLEMENTED 2026-09-29** on
`fix/076-live-mic-loss-and-echo` (all slices; see
[Implementation record](#implementation-record-2026-09-29)). Owner acceptance
on a packaged candidate and a quiet-machine `smoke:system-audio` are owed.
Two owner live streams on 0.9.120 (macOS), both with System audio. Priority **P0** for part A, since a
healthy microphone went silent for the rest of a live stream, and **P1** for
part B, since viewers heard the streamer's voice repeated.

Planned against main `18b8c5d5` (0.9.121). The bus code involved in part A
is unchanged from 0.9.120 on main.

## What the owner saw

1. **Stream 1.** System audio was on. About four minutes in, the microphone
   died and never came back. Toggling System audio off and on did not help,
   so the stream had to be ended.
2. **Stream 2.** Near the end, the owner turned System audio on to play some
   music. Viewers then heard the streamer's voice repeated ("is it working, is
   it working").

The two symptoms have **different causes**. Neither is caused by the
ScreenCaptureKit capture itself.

## Diagnosis

### A. The bus retires a healthy mic when its own output stalls (stream 1)

**Confirmed by a deterministic reproduction on main** (see
[Reproduction](#reproduction-run-during-this-investigation)). The path, as it
runs on main:

1. The session audio bus writes 10 ms chunks into a FIFO that FFmpeg reads.
   The cursor advances only when a chunk is written
   (`session_audio.rs` `run_bus_owned`, pacing ≈L3501–3514, write
   ≈L3766–3799). `write_rendered_chunk` (≈L4064) blocks until the reader
   drains. After 100 ms it swaps the rest of the chunk for zeros, but it still
   waits for the pipe.
2. Sources are placed against the **wall clock**. `SourceClock` maps each
   buffer's device time onto epoch-relative positions (≈L1949). A buffer is
   dropped if it lands more than `ahead_limit` (`MAX_BUFFERED_FRAMES` = 1 s,
   plus the bus delay) past the cursor (`AudioTimeline::push`, ≈L212).
   Queued audio older than wall − 1 s is discarded (`discard_before`, ≈L3496).
3. When FFmpeg stops reading, the cursor falls behind the wall clock. With the
   150 ms playout of system-audio platforms, every new mic and system buffer
   is dropped ahead-of-cap once the lag passes about 0.85 s. That is 0.95 s
   at the 50 ms mic-only playout.
4. `microphone_loss_reason` (≈L1829) treats 2 s without a placement
   (`NATIVE_AUDIO_SOURCE_STALL_TIMEOUT`, `audio.rs:40`) as `TimelineRejected`.
   The bus then **retires the producer** (≈L3444–3470). Nothing reopens it.
   `HandoffPurpose::Restore` exists only for a failed hot-swap. The rest of
   the session is generated silence. System audio has the same rule
   (`SYSTEM_UNPLAYABLE_LOSS_AFTER`, ≈L1827, and `SourceSlot::ingest_loss_at`).
   Its slot is retired as well, but the switch can re-attach it, so only the
   mic stays gone.

So a single output stall of about 3 s permanently silences a working mic.
The 2 s placement rule is **not new**: it dates from #389, and plan 070 only
split the reason for reporting. Plan 070 was right to report "kept
delivering but could not place". Retiring the producer on that verdict is
the bug.

**Why FFmpeg stopped reading** (likely, to be confirmed in slice A0). The
bundled FFmpeg is **8.1.1**, which has a threaded scheduler. It chokes a
demuxer whose output streams run ahead of the trailing output stream by more
than about 100 ms. When the recording or stream video input is late, the
audio input is paused, and FFmpeg stops draining the audio FIFO. The RTMP
outputs are already isolated (the `fifo` muxer with `drop_pkts_on_overflow`,
`recording.rs` ≈L16611), so a slow platform is not the trigger. The trigger
was machine-wide pressure, from opening Kick's player, that delayed video
into FFmpeg.

**System audio is a bystander here.** The SCK stream is audio-only (2×2 px at
1 fps, `system_audio_capture.rs` ≈L1229), and the same stall hits a
mic-only session. System audio only narrows the margin, through a 150 ms
playout instead of 50 ms. The owner's perception still stands: in this
session, turning System audio back on was the only visible control, and it
could not bring the mic back.

### B. System audio re-captures the streamer's own stream (stream 2)

Certain. The owner, the chat, and the loop signature all agree. SCK captures
what apps render, **whatever the output device**, so headphones do not stop
it. Plan 069 listed this under "Edge cases" as "FAQ; no auto-detection", and
per-app capture was out of scope. Its helper text today (`sources-tab.tsx:642`) says "Use headphones so your
mic doesn't pick it up twice". That advice is right for acoustic pickup, but
it suggests a protection that does not exist for this case. This is the
owner's own normal workflow: checking the stream in a tab while live. So the
decision to rely on documentation alone has failed in practice.

## Decisions (recommended defaults; the owner can overrule)

1. **Never retire a producer that is still delivering.** Retire only on
   `CaptureStopped`: EOF, no arrivals for the stall timeout, or a platform
   failure. `TimelineRejected` still emits its loss event (plan 070's
   reporting and the `AudioInputLost` quality flag stay), and then a
   **recovered** event when placement resumes.
2. **An output stall is not a source fault.** A buffer rejected while its
   mapped position still matches the wall clock is a bus-behind drop. It
   refreshes source liveness and never counts toward `TimelineRejected`.
3. **Echo guard: auto-pause, with a one-click Resume.** When System audio is
   confirmed to carry the mic's own voice back seconds later, the bus ramps
   the system contribution to zero. Capture keeps running, so Resume is
   instant. Waiting for a streamer to notice a warning lets a recursive loop
   run for minutes, which is what happened here. The alternative is
   warn-only; choose it if the owner prefers never to change the mix
   automatically.
4. Per-app capture (only certain apps, or excluding browsers) is the real
   prevention, but it is a separate plan (077). This plan fixes the
   misleading copy and adds detection.

### A1. Separate "the bus is behind" from "the source is wrong"

- `AudioTimeline::push` returns an outcome instead of `bool`: `Placed`,
  `Overlap`, `AheadOfCap { start }`, or `Malformed`. The counters and
  `BusLosses` fields stay exactly as they are.
- The bus already computes `wall_cursor` (≈L3490). Pass it into
  `ingest_pending` and `SourceSlot::place`. Handle an `AheadOfCap` result as
  follows:
  - If `start <= wall_cursor + ahead_limit`, the source is on time and the
    cursor is behind. It is a bus-behind drop. Refresh `last_source_frame`
    for the mic, and do not start or extend `unplayable_since` for the system
    slot. Count the frames in a new `BusLosses::dropped_output_stall` (a
    subset of ahead-of-cap), so logs show the split.
  - Otherwise the source clock is ahead of real time, and the existing
    `TimelineRejected` path applies.
- Refresh the call in the blocked-write `wait()` closure (≈L3746) the same
  way. That closure already ingests while the writer is blocked.
- Keep every law that plan 070 and #408 pinned: no cursor jump, no enlarged
  caps or timeouts, the stale-chunk policy unchanged, and a mic-only PCM
  golden SHA that stays byte-identical.

**Done when:** the A0 stall regression keeps the mic producer and reports no
loss, and output is audible again within 1 s of the reader resuming. The
stalled seconds stay silent, as today's drop policy requires. The plan 070
test `compositor::tests::static_screen_recording_epoch_keeps_current_audio`

### A2. A placement loss never retires; it recovers

- Split `microphone_loss_reason` into two parts. Retirement happens only on
  `CaptureStopped`. `TimelineRejected` pushes the `SourceLoss` event once,
  keeps `receiver` and `producer`, and marks the stats lost. The next
  successful placement marks it live again and pushes a `SourceRecovered
{ generation, after_ms, gap_ms }` event.
- If `TimelineRejected` persists, **re-anchor** the source once: set
  `clock = None` so the next buffer maps from `captured_at` against the
  epoch, the same as session start. Allow at most one re-anchor per 10 s, and
  log each with the before and after mapped positions. A re-anchor must never
  happen in a healthy session: assert 0 across the existing pressure and
  drift suites. This is a one-shot recovery after a hard fault, not the
  drift re-anchoring that 0.9.26 removed.
- Give the system slot the same treatment. `unplayable_lost` reports a loss
  and no longer calls `begin_exit(Lost)`. Platform failure and EOF still
  retire it (plan 069 decision 11).

**Done when:** these cases pass.

- The stall regression with a 6 s stall: the loss is reported, then
  recovery, the producer is never retired, and audio returns.
- A source-clock jump of +5 s is re-anchored and audio returns.
- EOF, disconnect, and no-arrivals still retire.
- The existing `real_lost_owner_…`, hot-swap, silent-drain, and system
  attach/detach tests pass unchanged.

### B1. Echo detector: the mic's own voice returning through System audio

- The bus already holds both signals per 10 ms chunk: the processed mic tap
  (`microphone_samples`) and the gained system contribution (`mixed.system`).
  Compute one onset value per chunk for each. Use the band-limited log
  envelope and its half-wave-rectified difference, as in the analysis above.
  Send the pair to a detector thread through a bounded `try_send`. Never run
  heavy work on the bus thread.
- Keep 32 s of mic history and 6 s of system history. Every 500 ms, compute
  the normalized cross-correlation of the last 5 s of system against the mic
  at lags from 0.3 s to 30 s. That covers Twitch low-latency, Kick, X, and
  YouTube.
- Declare a loop only when all of these hold:
  - the peak r clears an absolute floor and is at least 4× the p99 of the
    other lags;
  - the lag is stable within ±30 ms across 3 consecutive evaluations;
  - the mic had voice activity in the window;
  - system audio was above its floor.
    In stream 2 the peak was 0.30 against a p99 of 0.079, on the _mixed_
    track. On separated signals the margin will be far larger. Tune on
    fixtures, not on this number.
- Lags under 0.3 s are ignored. They mean the mic hears the speakers
  (acoustic pickup), which is a different problem and out of scope.
- Fixtures:
  - Positive: speech-like mic → system = mic delayed by 2.5, 3.16, 8, and
    20 s, AAC-coloured, at gains of -3 to -20 dB, with and without music
    mixed in.
  - Negative: music only; other people's speech; an old recording of the
    same voice (a different utterance); silence; a muted mic; and the mic
    picking up speakers at 20–60 ms.

**Done when:** every positive fixture is detected within 5 s and no negative
fixture fires across 10 minutes of each. The detector costs < 1% of one core
and adds no work to the bus thread's write path.

### B2. Echo guard: pause the system contribution, keep capture

- When a loop is detected, set a `guard_paused` flag on the system slot. The
  slot ramps to zero through the existing `EnableRamp`, and it stays attached
  and capturing. Publish the state in `SystemAudioObservation` and
  `recording.status.mix_sources`, and emit `system-audio-echo-paused` (warn)
  with the measured lag.
- Resume clears the flag, ramps back in, and re-arms the detector with a 3 s
  grace period. If the loop persists after that, it pauses again. "Keep on
  for this session" disables the guard until the session stops.
- Remote, Stream Deck, and phone: a `toggle` while paused means Resume. The
  deck key shows the paused state (plan 069 S6 surfaces).
- If the owner picks warn-only (decision 3), B2 emits the event and does not
  set the flag.

**Done when:** in a real-bus test, an injected loop pauses system audio within
5 s. The mic output stays byte-identical to a no-system run over the same
interval. Resume restores the signal sample-aligned, with no click at either
ramp.

## Reproduction run during this investigation

A throwaway test was added to `session_audio::mix_tests` on main `18b8c5d5`,
run once, and removed. Nothing was committed. It started a real bus with a
timed microphone delivering a constant (0.2, 0.2) for 9 s. A FIFO reader
read normally until 72,000 frames (1.5 s), stopped for 3 s, then resumed. No
system audio was attached.
`NATIVE_AUDIO_SOURCE_STALL_TIMEOUT` was the production 2 s.

| Playout                         | Loss event                     | State        | Audible 0.5–1.5 s | Audible 6.5–8.0 s |
| ------------------------------- | ------------------------------ | ------------ | ----------------- | ----------------- |
| 50 ms (mic-only)                | `TimelineRejected` at 4,652 ms | `SourceLost` | 48,000 / 48,000   | **0 / 72,000**    |
| 150 ms (system-audio platforms) | `TimelineRejected` at 4,756 ms | `SourceLost` | 48,000 / 48,000   | **0 / 72,000**    |

The counters were the same in both runs: captured 73,024, generated 310,976,
discarded 48,416, and dropped 96,960 (at 50 ms playout) or 101,760 (at 150
ms). The mic delivered until 9 s, but nothing after the stall reached the
output. That is stream 1 without system audio.

The harness, to rebuild as the A0 regression:

```rust
// A reader that stops draining the FIFO once, like FFmpeg pausing its
// audio input while video is late. Non-blocking reads, as spawn_fifo_reader.
fn spawn_stalling_fifo_reader(path: PathBuf, stall_after_frames: usize, stall: Duration)
    -> (thread::JoinHandle<Vec<u8>>, tokio::sync::watch::Receiver<usize>) {
    // ... identical to spawn_fifo_reader, plus at the top of the read loop:
    // if !stalled && bytes.len() / 8 >= stall_after_frames {
    //     stalled = true; thread::sleep(stall); last_data = Instant::now();
    // }
}

#[tokio::test(flavor = "multi_thread", worker_threads = 2)]
async fn output_stall_keeps_a_healthy_microphone() {
    for options in [SessionAudioOptions::default(), system_options()] {
        let epoch = Instant::now() + Duration::from_millis(100);
        let microphone = signal_packets(epoch, 0, 48_000 * 9, 480, |_| (0.2, 0.2));
        // producer: prepare_producer_with(timed_source(..)), as start_bus does
        // path: native_audio_fifo_path + create_native_audio_fifo
        let (reader, progress) =
            spawn_stalling_fifo_reader(path.clone(), 72_000, Duration::from_secs(3));
        let session = attach_prepared_with(source, path, Some(video_epoch),
            AudioProcessingSettings::default(),
            crate::audio::NATIVE_AUDIO_SOURCE_STALL_TIMEOUT, options);
        let bus = Bus { session, reader, progress };
        bus.wait_for_frames(48_000 * 8).await;
        // main today: claim_source_loss_event() == TimelineRejected,
        //             input_state() == SourceLost, 6.5-8.0 s all zero.
        // after A1-A2: no retirement; 6.5-8.0 s audible (72,000 / 72,000).
    }
}
```

### A. The bus never retires a healthy microphone

- `AudioTimeline::push_outcome` says why a packet was refused. An
  ahead-of-cap packet whose end is within the ahead limit of the wall-clock
  cursor was on time (`BusLosses::dropped_output_behind`).
- `OutputStall` (session_audio.rs): a bus that has kept pace and then falls
  250 ms or more behind is in a stall episode, which excuses on-time packets
  for up to 15 s. A bus that never kept pace (plan 070's old epoch) excuses
  nothing, so plan 070's regression and its "rejected, not stopped" test are
  unchanged.
- `TimelineFault`: a placement loss (`TimelineRejected`) is reported once,
  re-anchors the source clock at most every 10 s, never retires the producer,
  and reports its recovery (`SourceRecovery`, `SystemAudioRecovery`). Only a
  stopped capture (EOF, no arrivals, platform failure) retires a source. The
  system slot follows the same rule; `SlotHealth` carries the edges out of a
  blocked write.
- Health events: `audio-output-stalled` (warn, only when an episode cost
  audio; the owner's normal sessions, including the 59-minute stream, drop
  zero frames), `microphone-timeline-recovered` and `system-audio-recovered`
  (info). The quality gate's audio-loss codes are unchanged.

### B. The echo guard

- `echo_guard.rs`: `BandEnergy` (one ~300 Hz–4 kHz envelope value per 10 ms
  chunk, on the bus thread) and `EchoDetector` (on its own thread, fed by
  `EchoWatch`). Every second it correlates the last 4 s of system audio
  against 34 s of microphone history at 0.3–30 s lags. It fires when one lag
  wins four evaluations in a row with r >= 0.25 and 1.8x the 99th percentile
  of the other lags.
- Tuning (synthetic speech, strictly periodic music, recursive loops through a
  codec-like low-pass, numpy then Rust): the log-onset feature was masked by
  music, so the detector uses the linear envelope. Every loop from 2.5 to 20 s
  at -10 dB or louder is found at the exact lag within about 7-10 s of System
  audio coming on. 150 minutes of negatives (another voice, music, speaker
  pickup, and mixes) never fire: single evaluations reach 2.3x, and lag
  stability is what separates them. A -12 dB loop is not always caught, and
  that is accepted. This is slower than the plan's "within 5 s": the price of
  zero false positives.
- The bus ramps the system slot out on a detection (`SlotExit::EchoPaused`)
  and reports `system-audio-echo-paused` with the lag. The microphone output
  is untouched: the real-bus test checks it matches the microphone alone.
  `AudioSettings.systemAudioEchoGuard` (default on, live through
  `audio.processing.update`) turns the guard off; then a loop is only logged.
  The plan's "Keep on for this session" became this persistent switch in
  Sources.
- UI: Paused plus Resume in the mixer row, the Sources panel, and the Studio
  inputs, and a persistent toast with Resume. Resume re-sends System audio On
  (the same path as a shortcut) through a window event, so the lazy chunks
  stay out of the eager bundle. The shortcut and remote `toggle` while paused
  turns it Off, as for a loss; `on` resumes. The Sources helper text no longer
  implies headphones stop the loop.
